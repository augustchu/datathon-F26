# Source-grounded facility field recovery

Direction 01 takes a claim from a saved source through branch attribution, review, and publication. It produces inspectable evidence for resource counts, equipment and named services. Notebook 04a prepares the evidence once per snapshot. Notebook 04b uses approved service statements in the existing verification logic, and notebook 05 supplies approved resource and equipment fields to the three recommendation views. Lookup reads prepared assets. The original facility and training-label tables remain the authoritative record of what the dataset supplied.

## Implementation decisions

| Decision | Reason | Handling of edge cases |
| --- | --- | --- |
| Extract small claims with deterministic rules | The pilot has limited adjudicated data and the rules run on CPU without model downloads. Exact character offsets make each output inspectable. | Save candidates before review. A term match with ambiguous scope or an approximate, planned, historical, subunit or multi-branch count is withheld. English phrases and explicitly configured aliases limit recall. |
| Use saved original FDR text and bounded public-source capture | Both sources can hold useful details omitted from structured fields. Beautiful Soup provides reproducible text selection for a known public page. | FDR candidates retain the original record ID and candidate URLs. A URL on that record is a lead. Releasing a service through this pipeline requires a saved public passage with a direct URL. HTML capture and branch mapping are separate checks. |
| Require exact branch attribution for each public passage | The same organization can operate several hospitals. A group footer or a different page in a certificate can refer to another site. | Input must match a unique prepared branch by normalized name plus published PIN or address. Each eligible passage contains the exact saved branch anchor. A different six-digit PIN-shaped token makes the passage unresolved. This conservative check can also flag unrelated numbers. A reviewer checks statement scope within the passage, including names that share one PIN. |
| Keep the capacity basis and time separate | Total, licensed, operating and staffed beds can legitimately differ. Full-time, visiting and resident doctors are distinct measures. | Generic beds use `capacity` only for whole-facility totals. Defined subtypes use keys such as `capacity:staffed_beds` and `numberDoctors:full_time_doctors`. Whole-facility doctor totals need an explicit total and a source or assertion date. An explicit assertion date and the retrieval date are separate columns. Equipment subtype text stays in the ledger and displayed evidence. |
| Approve an immutable claim ID | Review should remain tied to the exact passage, branch, scope and value inspected. | A changed document, saved excerpt, source, value or extraction rule generates a new claim ID. Old approvals appear as `unmatched_review`. Future reviews, approvals before capture, expired validity, unresolved branch links and held locations are withheld. A dated service with an open-ended validity window needs review before it can enter recommendations. |
| Keep the original structured values and preserve disagreements | A second assertion can expose a difference without justifying an overwrite. Separate source and model layers make the result explainable. | A matching reported count stays reported. A reviewed disagreement with a structured value stays in the decision ledger. A malformed or conflicting original count needs review. Competing approved recoveries for the same field and basis produce a conflict sidecar, which suppresses a precise value in lookup. |
| Deduplicate evidence before counting publishers | Syndicated text and related publishers should contribute at most one independent support signal. | Identical or strongly similar normalized quotes, matching publisher families and matching organization hosts are consolidated. An explicit independence check is required before recovery can add support to an already supported service. Conflicting service evidence goes to the existing verification checks. |
| Keep recovery separate from live availability and estimates | A count or a named service is a source assertion with a scope. It has a different meaning from model output, appointments or staffed slots. | All modes show the same approved source evidence. Equipment appears as a facility field. Service eligibility still comes from explicit service wording and the existing prepared geometry and conflict checks. Recovered fields supply context. |

## Run and review

1. Run notebooks `01_source_eda` and `02_facility_and_geography` for the intended input mode, snapshot date and output path. The public-only mode can link reviewed documents against its prepared branches. Use `export` with a private FDR copy or `databricks` inside an authorized workspace for the original FDR rows.
2. Run `04_service_evidence` for the existing baseline. Run [04a source recovery](notebooks/04a_source_recovery.ipynb) to extract the audit candidates. Set `DATATHON_RECOVERY_DOCUMENTS` to a saved JSON document manifest when available. See the [public-source sample and scraper instructions](../data/recovery/SAMPLING.md).
3. Compare the value, scope, exact excerpt and source locator against the saved capture and the physical branch address. Each reviewer supplies one `approved` or `rejected` decision per claim ID and records a reason. Run 04a again with `DATATHON_RECOVERY_REVIEWS` pointing to the reviewed JSON list. The approval applies to the saved evidence assertion. For an independence decision, inspect attribution and look for shared original material.
4. Run `04b_verify_services`, `04c_facility_quality`, `05_field_updates` and `06b_prepare_lookup` to refresh the prepared outputs. The snapshot receipt binds releases to the exact upstream checkpoint content, aliases and release files. A changed input or partial write requires rerunning 04a. Old snapshots without recovery outputs continue to work.
5. Compare frozen queries with the same place input, travel mode, radius, service threshold and snapshot. Report newly supported branch–service pairs, separately from any count or equipment shown beside existing results. A count recovery may improve the explanation with the same rank and service options.

### Document and review records

Each saved document is a JSON object. Supply `document_id`, `facility_name`, `pin` or `address_contains`, optionally `city`, `publisher`, `publisher_family`, `source_url`, `retrieved_on` and an exact `branch_anchor`. Supply `passages` as objects with `text` and an optional positive integer `page`. Save the branch anchor in every passage that should be eligible. Passages carry the text as saved by the capture process. Character offsets refer to that text, including spaces and line breaks. The branch anchor must include the branch name and the location identifiers used for matching. Use optional `document_date`, `valid_from`, `valid_through` and `publication_scope` for explicit dates and scope. For text derived from a PDF, retain its actual page number and the association between the page statement and the branch. The HTML scraper handles the bounded sample. PDF transcription and OCR require separately saved passages and review.

Reviews are JSON objects with `claim_id`, `decision`, `reviewer`, `reviewed_on` and `reason`. Optionally set `independence_checked` to `true` after reviewing publisher and statement independence. An absent decision keeps the claim awaiting review. A reviewer can retain a claim for follow-up while withholding release by leaving it unapproved.

| Checkpoint | Contents |
| --- | --- |
| `recovery_claims` | Immutable source identifiers and hashes, claim type, raw and normalized value, unit and scope, stance, exact excerpt and offsets, source and retrieval dates, page, candidate URLs, publication scope and linkage basis. |
| `recovery_decisions` and `recovery_summary` | One decision per claim and any unmatched review, including attribution problems, original structured-count status, review outcome and release reason. The summary counts claims. |
| `recovered_field_updates` | Approved count and equipment sidecars labeled `source_recovered`, alongside any conflicts between reviewed candidates. The trace carries exact quotes and stable IDs. |
| `recovered_service_claims` | Approved, directly cited service assertions passed to the existing verification checks after duplicate screening. Both support and explicit contradictions carry scope and dates. |
| `recovery_snapshot` | A receipt binding release tables and project configuration to the prepared source snapshot. |

## What the pilot verified

The November 21, 2026 local export replay used 10,088 original FDR rows and a prepared catalogue of 41,489 branches. A sweep of four FDR text fields contributed 2,421 candidate claims. Of those, 2,188 were awaiting review on routable branches and 233 belonged to branches on location hold. The public-source sample yielded two approved Faridabad claims. Candidate counts are distinct from released facts and can include several claims for one facility.

| Field | FDR drafts | Approved public claims in this pilot |
| --- | ---: | ---: |
| Bed capacity | 957 | 1 |
| Doctor counts | 71 | 0 |
| Equipment | 126 | 0 |
| Named services | 1,267 | 1 |

The frozen NICU query for PIN 121001 used the postal origin and straight-line distance on both runs. Faridabad Medical Center went from excluded for insufficient traceable evidence to eligible from a single direct publisher, ranking first in all three modes in this replay. The prepared fields displayed its previously blank capacity as 35 beds with `source_recovered` provenance. This tests how published branch evidence changes the search. Live service availability and current bed occupancy require a separate, timely source. [Official Faridabad homepage](https://faridabadmedicalcenter.com/home/) · [Browser check, screenshots and withheld Arti claims](../data/recovery/SAMPLING.md)

Two failures sharpened the rules. A branch anchor in a different passage could wrongly cover a neighboring facility's statement. The passage gate now requires the anchor alongside the claim and checks for another PIN-shaped token. The first real replay classified the website correctly in service verification but withheld it in lookup because the two components used different labels for undated evidence. The adapter now uses lookup's existing `unknown` validity tier for a directly cited undated claim. Both cases have regression tests. A fictional replay also confirmed that unreviewed evidence stays out and an approved 55-bed total and MRI statement can flow into all three modes. The local suite passed 118 tests.

## How to evaluate recovery

Use [the evaluator](src/facility_tool/recovery_evaluation.py) with frozen cases and independently adjudicated decisions. Keep the reference value, field, branch, scope, stance and answerability separate from the candidate. Lock the case fingerprint before opening held-out results. Cases connected by branch, document family or passage digest belong together. Count wrong branches and unsupported citations separately from incorrect values, and count explicit abstentions. Reviewer time includes unsuccessful checks. Use independent-case intervals only when the unit and selection design justify them. The evaluation helper supports grouped uncertainty for linked cases. A purposely chosen example set measures behavior on those examples. Population yield needs a separate probability sample.

The [original research proposal](../possible-next-steps/01-source-grounded-field-recovery/README.md) describes 60 development cases, 120 locked distinct-facility cases, two reviewers, and comparisons with small or constrained generative extractors. This implementation establishes the deterministic baseline, reproducible evidence pipeline and evaluation contract. The independent review panel, comparative model runs, and full Free Edition deployment remain open. Same-record agreement and a small public-source spot check cannot establish population precision. The justification for measuring attribution separately from claim correctness follows the ALCE and Attribute or Abstain studies. [Gao et al.](https://aclanthology.org/2023.emnlp-main.398/) · [Buchmann et al.](https://aclanthology.org/2024.emnlp-main.463/)

## Use in future modeling

The pipeline writes source evidence only. For later supervised comparisons, select approved numeric claims whose basis matches the target, preserve their source labels, and use only the existing training partition. Keep the passage that supplied the target outside model inputs and check other fields for repeated or paraphrased counts. Report extraction correctness, new-label yield and imputation error independently. The prior description-label experiment recovered 12 blank counts, of which nine belonged to the training partition. Adding those nine produced no consistent test gain. [Prior model evaluation](../ML/MODEL_EVALUATION.md#using-counts-recovered-from-descriptions)
