# First prototype: implementation decisions

This file records the implementation choices made for the first Databricks prototype. It is intentionally explicit so the team can replace assumptions when better data becomes available.

## Product and architecture

1. The prototype is a Databricks App using Streamlit. It is intended for an authenticated hackathon demo, not anonymous/public patient access.
2. Data preparation runs separately in a Databricks notebook against Unity Catalog. The app reads a prepared Unity Catalog snapshot through a Databricks SQL warehouse. The app does not start a Spark session or rerun the full preparation pipeline after every UI interaction.
3. The app lives in this folder and imports only code shipped in this folder. No original project files are modified.
4. The preparation notebook explicitly reloads the shared `pipeline` module because Databricks notebook kernels cache imports across edits. It checks for required helpers and reports the loaded module path if the Git-folder copy is stale.
5. Prepared outputs use the existing `additional_india_data.default` schema confirmed by the team in the Volumes browser. Tables use the `first_prototype_` prefix to avoid collisions. This avoids assuming the absent `main` catalog or requiring `CREATE SCHEMA`. The notebook prints exact table names for App setup.
6. The source tables use catalog `databricks_virtue_foundation_dataset_dais_2026`, schema `virtue_foundation_dataset`, and the facilities, PIN directory, and NFHS district indicator table names. The catalog was corrected after the first Databricks run returned `TABLE_OR_VIEW_NOT_FOUND`; the notebook prints schemas/row counts so any further workspace-specific name changes are visible.
7. The supplied polygon archive is read from `/Volumes/additional_india_data/default/additional_india_data/geoBoundaries-IND-ADM2-all.zip`. The notebook reads its full GeoJSON member using `zipfile` and `json`, then does a WGS84 point-in-polygon join in Python. This avoids adding a GIS dependency to serverless compute. If no GeoJSON member is present, preparation stops with the archive member names in the error.
8. Regional population is joined from the tracked `load-balancing-pipeline/outputs/nfhs_district_population_2020.csv` file by normalized exact NFHS district and state names. It is read from the synced Git folder by default; `POPULATION_CSV` may override the path for a Volume copy. The estimate is a modeled 2020 value from a constrained WorldPop raster scaled to MoHFW/NCP state projections, not a fresh census or current population count. Missing, duplicate, or unmatched population keys remain unavailable; they are never filled with a guessed population.
9. `facilities_newest_capacity.csv` is the complete cleaned facility display source, not just a capacity overlay. Facility names, locations, coordinates, service evidence, source URLs, phone, and website are prepared from its rows. The Marketplace facilities table is retained only for source-snapshot/ID validation and capacity cross-checks. Bed capacity and confidence come from the two tracked files in `max-supplemented-data/capacity_and_confidence/`; Databricks Git-folder sync makes them available, so no separate download or Volume upload is required. The 10,088-row capacity and confidence files are validated for row count and continuous 0-based `row_index`. Confidence is paired to capacity by documented source-row order, then release rows are matched to Marketplace IDs using `unique_id` rather than relying on Spark's nondeterministic row order. Duplicate IDs are accepted only when all demo-used release values agree.
10. The capacity file's selected `capacity` is the calculation value. The notebook compares it with the current Marketplace capacity and separately checks the Marketplace capacity against the release's `original_capacity` to verify source alignment. Both outcomes are recorded and discrepancies reported; the selected release value stays authoritative. If the release explicitly withholds a count, the app does not reintroduce a possibly unsafe raw value. `xgboost_estimate` capacities are labeled **Estimated bed capacity**; held/missing values stay missing and only use the disclosed 50-bed scenario fallback.
11. Service match measures how directly the record addresses the requested service. An explicit listing earns 100 and a passing mention earns 40. Evidence confidence measures source support and branch identity. Official evidence with independent corroboration earns 80 service points, one official listing earns 75, a reviewed directory listing earns 70, an explicit facility-record listing earns 50, and a passing mention earns 15. The branch contributes up to 20. A confidence score of 90 or higher is High. Ranking uses both service scores. Phone and website use the release values first, with Marketplace fallback.

## Facility identity, service evidence, and citations

12. The first prototype preserves one source row as one facility candidate. It does not merge facilities with similar names because a wrong branch merge can make a recommendation unsafe.
13. The snapshot attaches reviewed claims by canonical branch ID, PIN, and the exact service, applying each claim's recorded validity dates. Reviewed claims retain their excerpts and links. A service entry in a specialty, capability, or procedure field, or a direct offering statement, can earn explicit facility-record credit. Relevant text with weaker scope earns passing-mention credit. General C-section and SNCU aliases receive passing-mention credit for emergency C-section and NICU searches. The matcher checks nearby wording for obvious negation, plans, and referrals elsewhere. General facility links are shown as record sources.
14. A result needs usable coordinates and either an eligible service excerpt from the facility record or a reviewed claim backed by an excerpt and source URL. A URL alone earns no service credit. An active reviewed conflict excludes the result.
15. Cards show the evidence label and matched excerpt. Reviewed claims link to the specific supporting source. General links from the facility record are labeled as record sources.
16. The prototype suppresses a match if the nearby text contains a simple negation such as “does not provide” or “not available.” This rule is intentionally basic and must be reviewed against false positives and false negatives.
17. The prototype detects only simple text negation and ADM2/NFHS name-join status. It does not fully detect merged facilities or contradictory addresses. Geography flags are shown on result cards; routing distance still uses the original source coordinates.

## Geographies and ranking

18. Users may enter coordinates, a PIN, a city, or a district. Text locations resolve to a centroid of matching facility coordinates when no geocoder is available; the app labels this origin approximate. Coordinates are used as entered and labeled user-provided.
19. The prototype uses haversine straight-line distance as its default travel measure so it works without a third-party API. It labels this as straight-line distance, not road travel time.
20. The app offers an optional routine-care comparison using published, branch-level monthly caseload and modeled throughput. It compares the baseline first choice with nearby alternatives that have the same service evidence kind, modeled scope, period, and unit. The comparison gives equal weight to the fraction of the permitted extra trip and projected demand divided by demand plus throughput. A winning alternative moves to the top. The [projection methods](../non-ml/caseload/NETWORK_CASELOAD.md) document the source and modeling limits.
21. The app's baseline ranking cost adds travel, service match adjustment, and evidence confidence adjustment. The historic population-scenario formula remains available to earlier replay callers that supply a nonzero population share.
22. The service match adjustment is `5 × (1 − match / 100)` in km-equivalent. Evidence confidence uses a logistic curve with a midpoint of 55, a width parameter of 3.5, and a ceiling of 60 minute-equivalents or 30 km-equivalent. At equal match and demand, confidence 90 can offset about 11.6 extra drive minutes compared with confidence 60. [Confidence-weight tradeoff](#confidence-weight-tradeoff)
23. The app displays released bed counts as context. The routine-care load comparison uses modeled throughput for the requested service.
24. Eligible records need service evidence and usable coordinates. The location screen checks the release routing flag, exact branch-point holds from `location_routing_holds.json`, coordinate bounds, and known out-of-boundary points. This screen also filters the rows used for city or PIN centroids. An explicit reviewed service conflict excludes the record. If no eligible result remains, the app reports the evidence gap.
25. For services with a matching NFHS field, the preparation step computes a district value relative to the national mean, halves parenthesized low-confidence values, and clips the result to 0.5–2.0. That factor scales synthetic load pressure on facilities mapped to the district. The service-to-field mappings are name-hint heuristics; unsupported services and unmatched regions use 1.0. NFHS percentages are survey indicators, not disease incidence or case counts.

## Models

26. The release capacity is used for capacity calculations wherever populated; its `capacity_status`, source, source URL, and estimate interval are carried through to the prepared snapshot. Capacity never determines whether the facility offers the requested service.
27. A release estimate retains `xgboost_estimate` provenance and is explicitly described as an estimate. A held or missing release capacity is not silently backfilled by the older neural model or by the source field the release withheld.
28. Phone and website are carried into each prepared facility card. Missing contact details are shown as “Not listed in the available records”; external website and capacity-source URLs are rendered as links when present.

## Interactive controls and persistence

29. The app opens on the search controls and loads the snapshot after the user submits a search. Results include a collapsed **Search options** panel that reranks as inputs change. **Back to search** hides the results and restores the full controls with their current values.
30. Population share creates a deterministic hypothetical district-level scenario. Equal allocation is over eligible facility records in each district. Emergency ranking uses travel, service match, and evidence confidence.
31. The app reads from a named prepared table and uses a bounded cache. Re-run preparation and increment/update the snapshot timestamp to refresh cached data.
32. TravelTime uses a typical weekday-morning arrival period and a three-hour search window. A partial matrix ranks the reachable facilities. A successful response with zero reachable facilities shows a banner above the map and sorts eligible results by straight-line distance alone. Provider and credential errors use the regular distance-based ranker.
33. TravelTime ranking uses route minutes and converts all km-equivalent adjustments at 2 minutes per km-equivalent. Regular distance ranking adds the same adjustments to straight-line kilometers. Both modes show travel and a unitless **Ranking score** separately. The **More info** panel for that score explains the adjustments. Other calculated values have their own **More info** panels with their meaning, calculation, rationale, and repository sources.
34. The app only reads data. It does not persist patient location, searches, feedback, or health information.

## Scoring and ranking evolution

- **Original release confidence.** The capacity release assigned up to 20 points each for branch name and PIN, phone, documented services, beds, and doctors. A verified unchanged value earned 20, a verified correction or fill earned 15, and a populated or corrected value awaiting independent confirmation earned 5. Estimated, missing, and held values earned zero. All 10,088 exported scores reconciled with the rubric. The median was 10 and the mean was 13.72. The earlier app ranked with a 0, 40, or 80 km-equivalent adjustment for scores of 50–100, 25–49, or below 25 or unknown, respectively. [Capacity release scoring](../max-supplemented-data/experiments/capacity/NEWEST_CAPACITY_RELEASE.md#2-calculate-confidence-from-five-important-cells)
- **Service-specific evidence.** The current app gives explicit listings 100 for service match and passing mentions 40. Evidence confidence awards 80 service points for corroborated official evidence, 75 for one official listing, 70 for a reviewed directory, 50 for an explicit facility record listing, and 15 for a passing mention. A confirmed branch adds 20 points and a plausible branch name and PIN add 10. With no service evidence the score is zero and the result is excluded. Audited location holds and active reviewed service conflicts also exclude results.
- **Location screening.** The November 21 location audit supplied 509 additional holds on branch and coordinate pairs in the frozen release. The app applies them to result eligibility, routing, and the facility points used for city and PIN origins. [Location audit](../non-ml/LOCATION_AUDIT.md) · [Hold list](location_routing_holds.json)
- **Ranking weights.** The service match adjustment is capped at 10 minute-equivalents. Confidence used linear caps of 5 and 15, a piecewise hour-scale trial, and an initial 60-minute logistic curve centered at 75. The current logistic baseline keeps the 60-minute ceiling and concentrates the penalty increase in the 50s as confidence falls from 100. [Ranking implementation](pipeline.py)

## Confidence-weight tradeoff

**Working baseline for the prototype. The broader weighting decision remains open.** We use the hour-scale logistic curve as the baseline for the next comparison. How much extra travel stronger documentary evidence should justify is partly subjective. It depends on urgency, the available alternatives, and how well the evidence reflects the service the patient needs. The ceiling, midpoint, and steepness are prototype choices that require further consideration.

An explicit facility record earns 50 service points. A plausible branch name and PIN add 10, bringing that result to confidence 60. Under the initial logistic curve, that result picked up 57.14 minute-equivalents, close to the hour ceiling. Moving the midpoint from 75 to 55 lowers its adjustment to 11.60. As confidence falls from the high end, the penalty now rises sharply in the 50s. At 50 the penalty reaches 48.40, and a passing mention with plausible branch identity scores 25 and adds almost the full hour. This gives a typical explicit facility listing room to rank competitively on travel time while still strongly penalizing sparse evidence.

The ceiling limits the largest possible confidence adjustment. The difference between two adjustments determines how much extra travel stronger evidence can offset when service match and demand are equal. Confidence 90 can now offset about 11.6 extra drive minutes compared with confidence 60. When the total costs tie, the closer route ranks first.

| Confidence weighting | Adjustment at 60 | Adjustment at 90 | Drive-time difference it can offset |
| --- | ---: | ---: | ---: |
| Previous linear scale, 15-minute ceiling | 6.0 min | 1.5 min | 4.5 min |
| Alternative linear scale, 60-minute ceiling | 24 min | 6 min | 18 min |
| Piecewise trial, 60-minute ceiling | 53 min | 2 min | 51 min |
| Initial logistic scale, 60-minute ceiling, midpoint 75 | 57.14 min | 2.46 min | 54.67 min |
| Current logistic baseline, 60-minute ceiling, midpoint 55 | 11.60 min | 0.003 min | 11.60 min |

Differences are calculated before rounding.

For confidence `c`, set `s(c) = 1 / (1 + exp((c − 55) / 3.5))`. The minute-equivalent adjustment is `60 × (s(c) − s(100)) / (s(0) − s(100))`. This sets the endpoints to 60 and 0. Divide by 2 for km-equivalent in straight-line mode.

| Evidence confidence | 0 | 25 | 50 | 55 | 60 | 65 | 70 | 100 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Adjustment in minute-equivalents | 60 | 59.99 | 48.40 | 30.00 | 11.60 | 3.26 | 0.81 | 0 |

Reducing the width parameter from 5 to 3.5 makes the transition steeper. The penalty changes by about 4.29 minutes per confidence point right at 55. The initial curve changed by about 3.02 minutes per point at 75. A classification error near the new midpoint can therefore move a result across several minutes of travel cost. The midpoint and slope express a subjective ranking preference that remains open to revision. The same confidence adjustment applies across urgency modes. Further consideration should compare actual drive routes, examine services and regions with sparse reviewed evidence, and assess the acceptable tradeoff separately for routine, urgent, and emergency searches.

A successful TravelTime response with no reachable results still displays the banner and orders eligible facilities by straight-line distance alone. The evidence and match scores remain visible on those cards.

## Replay validation

- **Service scores.** The reviewed-only version returned three results. Admitting eligible facility record text brought the count to 8,000. Separating explicit listings from passing mentions added 35 confidence points to 2,444 results without changing the eligible set. The resulting snapshot had 2,447 direct matches, including three with reviewed evidence, and 5,553 passing mentions. - **Ranking update.** The replay used all nine services from the Jaipur, New Delhi, and Bengaluru facility centroids. It used routine mode, a 0% demand scenario, and the same straight-line distances in both passes. Moving from the legacy release confidence adjustment to the first service-specific ranker changed 23 of 27 winners and the top-three membership in 24. Winners with a direct match increased from 8 to 24, and mean winner distance went from 19.10 to 9.39 km. - **Confidence weight.** Raising the cap from 5 to 15 minute-equivalents changed zero of 27 winners, top-three membership in three searches, and top-three order in four. Mean top-three evidence confidence rose from 51.79 to 52.90, and mean top-three distance rose from 19.97 to 20.09 km. For Jaipur maternity, Soni Hospital moved from sixth to third with confidence 70 at 2.85 km. Jaipur Hospital moved from second to sixth with confidence 50 at 1.80 km. - **Piecewise hour-scale trial.** Replaying the same 27 routine straight-line searches against the 15-minute linear setting changed three winners, top-three membership in one search, and top-three order in three. All three changed winners had 100 service match under both policies. Mean winner confidence rose from 59.07 to 61.11, and mean winner distance rose from 9.39 to 10.02 km. The largest distance increase was Delhi NICU. The top result moved from Triton Hospital at 9.22 km and confidence 60 to Faridabad Medical Center at 23.52 km and confidence 95. - **Initial hour-scale logistic trial.** The curve centered at 75 gave the same winners as the piecewise trial across 27 searches, with one change in top-three membership. New Delhi general care placed Amrit Clinic third at 3.87 km with match 40 and confidence 25. It displaced Dashmesh Hospital at 8.75 km with match 100 and confidence 60. That shift illustrates how the initial logistic curve compressed penalties below its midpoint. Compared with the 15-minute linear scale, three winners and two top-three memberships changed. In New Delhi NICU, Triton Hospital at 9.22 km and confidence 60 moved above Faridabad Medical Center at 23.52 km and confidence 95. Both had service match 100. Mean winner distance fell from 10.02 to 9.49 km and mean winner confidence fell from 61.11 to 59.81. Across all top-three positions, mean distance rose from 20.21 to 20.98 km and mean confidence rose from 53.33 to 55.62. The first-place example shows how a clear facility listing in the 60s can compete on distance. The scores and weights are prototype heuristics. The replay measures ranking changes on a frozen snapshot using a distance proxy. Tests cover driving-minute and zero-reachability behavior with fixed route inputs. Evidence labels describe available documentation, and current staffing and service availability need separate verification.

## Known limitations before any real-world use

35. The app is a hackathon decision-support demonstration. It must not be used as a clinical triage system, emergency dispatch service, or guarantee that treatment is currently available.
36. Text search, negation, address resolution, population joins, confidence calibration, and heuristic ranking can be wrong. Service confirmation, source date/validity, exact branch matching, calibrated evidence tiers, validated issue-to-indicator mappings, actual catchment/population assignment, and observed service-level availability/load are future work.
37. The preparation notebook is designed to surface schema and geography mismatches instead of silently guessing. Team members must review its output counts, rejected rows, and sample recommendations in Databricks before presenting results.
