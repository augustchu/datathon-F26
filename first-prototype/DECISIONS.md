# First prototype: implementation decisions

This file records the implementation choices made for the first Databricks prototype. It is intentionally explicit so the team can replace assumptions when better data becomes available.

## Product and architecture

1. The prototype is a Databricks App using Streamlit. It is intended for an authenticated hackathon demo, not anonymous/public patient access.
2. Data preparation runs separately in a Databricks notebook against Unity Catalog. The app reads a prepared Unity Catalog snapshot through a Databricks SQL warehouse. The app does not start a Spark session or rerun the full preparation pipeline after every UI interaction.
3. The app lives in this folder and imports only code shipped in this folder. No original project files are modified.
4. The preparation notebook explicitly reloads the shared `pipeline` module because Databricks notebook kernels cache imports across edits. It checks for required helpers and reports the loaded module path if the Git-folder copy is stale.
5. Prepared outputs use the existing `additional_india_data.default` schema confirmed by the team in the Volumes browser. Tables use the `first_prototype_` prefix to avoid collisions. This avoids assuming the absent `main` catalog or requiring `CREATE SCHEMA`. The notebook prints exact table names for App setup.
6. The source tables use catalog `databricks_virtue_foundation_dataset_dais_2026`, schema `virtue_foundation_dataset`, and the facilities, PIN directory, and NFHS district indicator table names. The catalog was corrected after the first Databricks run returned `TABLE_OR_VIEW_NOT_FOUND`; the notebook prints schemas/row counts so any further workspace-specific name changes are visible.
7. The supplied polygon archive is read from `/Volumes/additional_india_data/default/additional_india_data/geoBoundaries-IND-ADM2-all.zip`. The notebook reads its full GeoJSON member using `zipfile` and `json`, then does a WGS84 point-in-polygon join in Python. This avoids adding a GIS dependency to serverless compute. If no GeoJSON member is present, preparation stops with the archive member names in the error.
8. Regional population is joined from the tracked `load-balancing-pipeline/outputs/nfhs_district_population_2020.csv` file by normalized exact NFHS district and state names. It is read from the synced Git folder by default; `POPULATION_CSV` may override the path for a Volume copy. The estimate is a modeled 2020 value from a constrained WorldPop raster scaled to MoHFW/NCP state projections, not a fresh census or current population count. Missing, duplicate, or unmatched population keys remain unavailable; they are never filled with a guessed population.
9. `facilities_newest_capacity.csv` is the complete cleaned facility display source, not just a capacity overlay. Facility names, locations, coordinates, service evidence, source URLs, phone, and website are prepared from its rows. The Marketplace facilities table is retained only for source-snapshot/ID validation and capacity cross-checks. Bed capacity and confidence come from the two tracked files in `max-supplemented-data/capacity_and_confidence/`; Databricks Git-folder sync makes them available, so no separate download or Volume upload is required. The 10,088-row capacity and confidence files are validated for row count and continuous 0-based `row_index`. Confidence is paired to capacity by documented source-row order, then release rows are matched to Marketplace IDs using `unique_id` rather than relying on Spark's nondeterministic row order. Duplicate IDs are accepted only when all demo-used release values agree.
10. The capacity file's selected `capacity` is the calculation value. The notebook compares it with the current Marketplace capacity and separately checks the Marketplace capacity against the release's `original_capacity` to verify source alignment. Both outcomes are recorded and discrepancies reported; the selected release value stays authoritative. If the release explicitly withholds a count, the app does not reintroduce a possibly unsafe raw value. `xgboost_estimate` capacities are labeled “This is an estimated capacity”; held/missing values stay missing and only use the disclosed 50-bed scenario fallback.
11. Confidence is the release's fixed-denominator 0–100 data-quality score over identity/location, phone, services, beds, and doctors. It is not a probability of quality, clinical appropriateness, or current service availability. Phone uses the release's selected published phone first and then the Marketplace phone; website uses the release's official/website fields first and then the Marketplace fields.

## Facility identity, service evidence, and citations

12. The first prototype preserves one source row as one facility candidate. It does not merge facilities with similar names because a wrong branch merge can make a recommendation unsafe.
13. Service evidence is extracted from the facility's structured specialties, capabilities, procedures, equipment, and description fields. Matched terms and the original source text are kept in the prepared table.
14. A result is eligible only when a requested service term appears in facility text and at least one source URL is present. This is a conservative prototype rule, not proof of current operation. A facility lacking a link is not recommended, even if its text matches.
15. The app shows the matched excerpt and source URL on every result. This first prototype does not establish independent corroboration or source validity dates; these remain required next improvements before real use.
16. The prototype suppresses a match if the nearby text contains a simple negation such as “does not provide” or “not available.” This rule is intentionally basic and must be reviewed against false positives and false negatives.
17. The prototype detects only simple text negation and ADM2/NFHS name-join status. It does not fully detect merged facilities or contradictory addresses. Geography flags are shown on result cards; routing distance still uses the original source coordinates.

## Geographies and ranking

18. Users may enter coordinates, a PIN, a city, or a district. Text locations resolve to a centroid of matching facility coordinates when no geocoder is available; the app labels this origin approximate. Coordinates are used as entered and labeled user-provided.
19. The prototype uses haversine straight-line distance as its default travel measure so it works without a third-party API. It labels this as straight-line distance, not road travel time.
20. The slider is the percentage of each facility's NFHS district population assumed to need the selected service (0.0–2.0%, 0.1 point increments). For every district represented by an evidence-backed, coordinate-valid candidate, expected demand = modeled district population × percentage / 100. That district demand is divided evenly across all such facility source records in the district. The app does not route all demand to the nearest hospital. It also does not claim that all population lives within that hospital's actual catchment.
21. Routine/urgent score = straight-line kilometers + `12 × (1 − exp(−allocated cases / bed proxy × relative NFHS factor))` + data-confidence adjustment. Emergency skips the regional-demand component but still includes confidence adjustment. The demand penalty is capped at 12 km-equivalent; the exponential curve and cap are hand-set demo assumptions, not measured waiting time, occupancy, probability, or calibrated utility.
22. Confidence adjustment tiers are High (50–100) +0 km, Medium (25–49) +40 km, Low (0–24) +80 km, and unknown +80 km. These hand-set km-equivalent penalties intentionally make a 50 km High candidate rank ahead of a 25 km Medium candidate, which ranks ahead of a 5 km Low candidate when their demand-load adjustments are comparable. This is a ranking policy, not a clinical or statistical calibration.
23. Bed count is not current staffed capacity, available beds, or service-specific slots. It is only a coarse resource proxy. Release bed count is used when present; held/missing values use a disclosed 50-bed fallback only in the scenario formula. The UI shows the denominator and allocated hypothetical cases. Missing regional population means no demand-load adjustment is applied.
24. Missing or invalid coordinates and records without citable service evidence are omitted. If no eligible record remains, the app abstains and explains that it could not find a sufficiently supported option.
25. For services with a matching NFHS field, the preparation step computes a district value relative to the national mean, halves parenthesized low-confidence values, and clips the result to 0.5–2.0. That factor scales synthetic load pressure on facilities mapped to the district. The service-to-field mappings are name-hint heuristics; unsupported services and unmatched regions use 1.0. NFHS percentages are survey indicators, not disease incidence or case counts.

## Models

26. The release capacity is used for capacity calculations wherever populated; its `capacity_status`, source, source URL, and estimate interval are carried through to the prepared snapshot. Capacity never determines whether the facility offers the requested service.
27. A release estimate retains `xgboost_estimate` provenance and is explicitly described as an estimate. A held or missing release capacity is not silently backfilled by the older neural model or by the source field the release withheld.
28. Phone and website are carried into each prepared facility card. Missing contact details are shown as “Not listed in the available records”; external website and capacity-source URLs are rendered as links when present.

## Interactive controls and persistence

29. The app exposes service, origin, severity, regional population share (0–2%), and result count. Every control is passed to the ranking function. The Find button starts a search; after that, Streamlit reruns and updates results on widget changes.
30. Population share creates a deterministic hypothetical district-level scenario for ranking only. Equal allocation is over selected-service facility source records with citable text and valid coordinates in each district; the dataset may contain duplicates, merged records, and facilities that no longer operate. The calculation does not create real patients or change source data. Emergency ranking ignores simulated load but still applies the confidence adjustment.
31. The app reads from a named prepared table and uses a bounded cache. Re-run preparation and increment/update the snapshot timestamp to refresh cached data.
32. When enabled (default), the app makes one TravelTime Fast one-to-many request for all evidence-backed, coordinate-valid facilities matching the selected service. It uses `TRAVELTIME_APP_ID` and `TRAVELTIME_API_KEY` from the Databricks App environment, `driving+ferry`, a typical `weekday_morning` arrival period, and the provider's 3-hour search limit. The result is cached for 30 minutes so changing the population-share slider does not repeat the API request. If credentials, outbound network access, provider response, or reachability are unavailable, the UI identifies the condition and falls back to the existing straight-line kilometer score. An individual unreachable destination is excluded in TravelTime mode rather than being assigned a fabricated route time.
33. The TravelTime score uses route minutes plus load and confidence penalties converted from their existing km-equivalent values using 2 minutes per km (1 minute â‰ˆ 0.5 km). Straight-line fallback continues to use kilometers and the original penalties. This unit conversion preserves the prototype's relative ranking policy; neither it nor the route estimates are calibrated clinical or availability measures.
34. The app only reads data. It does not persist patient location, searches, feedback, or health information.

## Known limitations before any real-world use

35. The app is a hackathon decision-support demonstration. It must not be used as a clinical triage system, emergency dispatch service, or guarantee that treatment is currently available.
36. Text search, negation, address resolution, population joins, confidence calibration, and heuristic ranking can be wrong. Service confirmation, source date/validity, exact branch matching, calibrated evidence tiers, validated issue-to-indicator mappings, actual catchment/population assignment, and observed service-level availability/load are future work.
37. The preparation notebook is designed to surface schema and geography mismatches instead of silently guessing. Team members must review its output counts, rejected rows, and sample recommendations in Databricks before presenting results.
